# Развёртывание и запуск

## 1. Стенд проверки

Сведения организаторов о проверяющем стенде и как решение их учитывает:

| Условие стенда | Как учтено |
|---|---|
| Не более 1× H100 80 ГБ на команду; GPU может использоваться несколькими командами | одна карта (`count: 1`); доля памяти vLLM — `INSPECTOR_LLM_GPU_MEMORY` (по умолчанию 0.85). vLLM резервирует долю от **всей** памяти карты: если GPU общий, задайте долю под фактически свободный объём (7B-модели достаточно 0.5) |
| 24 ядра / 48 потоков, до 640 ГБ ОЗУ | лимиты `deploy.resources.limits` в `docker-compose.yml`: основной состав — 43 потока и 365 ГБ, с профилями мониторинга и логов — 46 потоков |
| Диск от 300 ГБ | образы ≈ 40 ГБ, веса ≈ 17 ГБ; данные, копии и логи — в именованных томах |
| GPU через NVIDIA Container Toolkit, драйвера в образе нет | драйвер NVIDIA ставится на хост; CUDA runtime входит в образ `vllm/vllm-openai`; номер карты — `INSPECTOR_GPU` |
| Подключение к собственному публичному API команды запрещено | всё работает внутри контура: сеть `contour` объявлена `internal`, адрес модели вне контура отклоняется кодом |
| CPU-режим не обязателен, нормативы — на GPU | модель работает только на GPU; остальные сервисы — на CPU |
| Проверка после дедлайна, окна объявят | комплект собирается заранее (раздел 3) и запускается без сети |

Распределение ресурсов (основной состав):

| Сервис | CPU | ОЗУ | Назначение |
|---|---|---|---|
| llm | 8 | 96 ГБ | vLLM на GPU |
| ml-worker × 4 | 5 каждая | 48 ГБ каждая | разбор, OCR, CV, проверка; одна задача на реплику |
| ml-api | 4 | 16 ГБ | изображение листа, метрики, проверка правил |
| server | 4 | 16 ГБ | REST API, база, хранилище |
| redis | 2 | 32 ГБ | кэш разбора (24 ГБ под данные, вытеснение LRU) |
| rabbitmq, clamav | 2 + 2 | 4 + 8 ГБ | очередь, антивирус |
| frontend | 1 | 1 ГБ | nginx, TLS 1.3 |

Число реплик воркера — `INSPECTOR_ML_WORKERS` (по умолчанию 4); при
изменении лимиты пересчитать так, чтобы сумма не превышала 48 потоков.

## 2. Подготовка секретов

```bash
scripts/make-secrets.sh
```

Создаёт в `./secrets` ключ базы (SQLCipher), ключ хранилища оригиналов, ключ
кэша ML и служебный токен сервер ↔ ML, а в `.env` — пароли RabbitMQ и Redis.
Если сертификат заказчика ещё не установлен, создаёт в `./certs` локальный
сертификат для `localhost`; перед доступом по имени или IP стенда замените его
сертификатом с соответствующим SAN. Без сертификата основной состав не стартует.
Существующие ключи не перезаписываются: потеря ключа базы — потеря данных,
их резервная копия — забота администратора. В git каталог `secrets/` и
`.env` не попадают.

Прочие настройки — `.env` по образцу `.env.example`: пароль администратора,
модель, доля памяти GPU, число реплик воркера, адрес ИАИС «РиН».

## 3. Офлайн-комплект

На машине с Интернетом, один раз:

```bash
scripts/offline/prepare_bundle.sh
```

Собирает образы (server, ml, frontend, vLLM по дайджесту, RabbitMQ, Redis,
ClamAV, мониторинг, ELK), скачивает веса Qwen2.5-VL-7B-Instruct и модель
эмбеддингов в ONNX, базы сигнатур ClamAV и пишет `bundle/MANIFEST.txt`
(ревизии весов, ID образов, SHA-256 файлов).

На стенде (без Интернета) — каталог репозитория вместе с `bundle/` и
`models/`:

```bash
scripts/offline/load_bundle.sh
```

Загружает образы, сверяет их ID с манифестом, создаёт секреты, кладёт базы
антивируса в том и поднимает состав. Первый запуск модели — несколько минут
(загрузка весов в GPU): `docker compose ps`.

### Веса моделей

Каталог `models/` в git не входит. Раскладка:

```text
models/
├── Qwen2.5-VL-7B-Instruct/                 config.json, *.safetensors, токенизатор
└── paraphrase-multilingual-MiniLM-L12-v2/  tokenizer.json, onnx/model.onnx
```

Копия весов команды (≈ 17 ГБ) — папка на Яндекс.Диске:
**https://disk.yandex.ru/d/fRWLLBTKeV1CXw**

Скачивать вручную не нужно: при `docker compose up` (или `scripts/start.sh`)
разовый сервис `models` сам кладёт веса в `models/`, если их там нет, — с
Яндекс.Диска, а при его недоступности с Hugging Face
(`Qwen/Qwen2.5-VL-7B-Instruct`,
`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`). Модель и
ML-модули стартуют только после него. Другая папка с весами —
`INSPECTOR_MODELS_URL` в `.env`. На стенде без Интернета веса кладутся в
`models/` заранее (вручную или офлайн-комплектом), и сервис ничего не качает.

Перед запуском проверить, что веса полные и модель эмбеддингов работает:

```bash
docker compose run --rm --no-deps ml-api python -m app.check_models
```

Без Docker — `INSPECTOR_MODELS_DIR=models PYTHONPATH=packages/ml
.venv/bin/python -m app.check_models`. Код выхода 0 — обе модели готовы;
иначе в выводе названы недостающие или пустые файлы.

## 4. Запуск и проверка

```bash
docker compose up -d                                   # основной состав
docker compose --profile monitoring up -d              # + Prometheus, Grafana, Alertmanager
docker compose --profile logging up -d                 # + Elasticsearch, Logstash, Kibana
```

| Адрес | Что |
|---|---|
| `https://стенд:5443` | интерфейс; TLS 1.3, сертификат `certs/server.crt` и ключ `server.key` обязательны |
| `https://стенд:5443/api/v1` | REST API; схема — `/api/v1/openapi.json` |
| `http://стенд:9090`, `:3000` | Prometheus, Grafana (профиль monitoring) |
| `http://стенд:5601` | Kibana (профиль logging) |

Первый вход — `admin` / `admin` (или `INSPECTOR_ADMIN_LOGIN` /
`INSPECTOR_ADMIN_PASSWORD` в `.env` до первого запуска). Учётные записи
проверяющих заводит администратор: «Администрирование» → «Пользователи».

Метрики сервера Prometheus читает токеном учётной записи роли `service`:
создать её, получить токен (`POST /api/v1/auth/login`, поле `token`) и
положить в `deploy/monitoring/metrics-token`. Адреса и токены доставки
алертов — в `deploy/monitoring/alertmanager.yml` и файлах `secrets/smtp.password`,
`secrets/telegram.token`.

## 5. Что нажимать

1. **Проверка ПД → РД → ИД** → загрузить тома (PDF, DOCX, XML, DWG, DXF) и
   заполнить карточку каждого: объект, стадия, шифр, редакция, статус
   утверждения, предшественник. Или загрузить пакет с реестром через API.
2. Выбрать объект и документы → «Запустить проверку». Ход виден по этапам,
   проверку можно остановить.
3. Разобрать протокол: у кандидата — ожидаемое и фактическое значение,
   доказательства на листах с подсветкой области. Решение: подтвердить, не
   подтвердить (с кодом причины) или запросить уточнение.
4. «Завершить» — когда решены все кандидаты; протокол выгружается в PDF,
   DOCX, XML, JSON.

## 6. Разработка без Docker

```bash
make install
# RabbitMQ и Redis — локально или в контейнерах; переменные:
export INSPECTOR_AMQP_URL=amqp://guest:guest@127.0.0.1:5672/ INSPECTOR_REDIS_URL=redis://127.0.0.1:6379/0
export INSPECTOR_ML_URL=http://127.0.0.1:8090 INSPECTOR_SERVER_URL=http://127.0.0.1:8010
export INSPECTOR_LOCAL_LLM_URL=http://127.0.0.1:8000 INSPECTOR_COOKIE_SECURE=0
make server   # в одном терминале
make ml       # во втором
make web      # в третьем: http://localhost:5173
```

Вне промышленного режима ключи шифрования сервера создаются в
`packages/server/dev-secrets/` (в git не идут), служебный токен ML берётся из
`INSPECTOR_INTERNAL_TOKEN`.

## 7. Если что-то не работает

| Симптом | Причина и что делать |
|---|---|
| процесс `ERROR`: «локальная модель не отвечает» | сервис `llm` не запущен или веса ещё грузятся: `docker compose ps`, `docker compose logs llm` |
| vLLM падает с нехваткой памяти GPU | карта занята другими: уменьшить `INSPECTOR_LLM_GPU_MEMORY` |
| загрузка отклонена: «антивирус не подключён» | сервис `clamav` ещё загружает базы (до 5 минут) |
| `docker compose` требует `INSPECTOR_AMQP_PASSWORD` | не запущен `scripts/make-secrets.sh` |
| «файл больше допустимого» | 50 МБ на файл и 200 МБ на пакет (ТЗ 9.1) |
| семантика `not_configured` | нет `models/paraphrase-multilingual-MiniLM-L12-v2` — собрать комплект заново |
